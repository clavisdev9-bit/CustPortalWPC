## CR-001 — Tangani conflict identity mapping dengan 409, bukan 500 mentah

- **Tanggal**: 2026-08-22
- **Terkait**: [BUG-01](resolution.md#bug-01--post-users-crash-500-mentah-saat-partner-odoo-sudah-terhubung-ke-user-lain)

- **Alasan**: Sebelumnya, mencoba membuat portal user kedua untuk kontak Odoo yang sama menghasilkan `500 internal_error` generik yang membocorkan detail constraint database mentah ke response API dan tidak memberi petunjuk apa pun ke admin tentang apa yang sebenarnya salah.
- **Dampak**: `POST /users` — tidak ada perubahan pada permission/skema request, hanya perilaku response error untuk kasus konflik ini.

## CR-002 — Deteksi "invoice lunas" juga mencakup status `in_payment`

- **Tanggal**: 2026-08-23
- **Terkait**: [BUG-02](resolution.md#bug-02--notifikasi-invoice-lunas-tidak-pernah-muncul-untuk-pembayaran-lewat-jurnal-bank-standar)

## CR-003 — Normalisasi error UUID malformed jadi 400, bukan 500

- **Tanggal**: 2026-08-23
- **Terkait**: [BUG-03](resolution.md#bug-03--uuid-path-param-yang-salah-format-bocor-sebagai-500-mentah-bukan-400)
- **File diubah**: `src/middleware/errorHandler.js`
- **Perubahan**: Menambahkan penanganan khusus untuk kode error Postgres `22P02` (invalid_text_representation) sebelum fallback generik 500 — dikembalikan sebagai `400 bad_request` dengan pesan "Invalid id format".
- **Alasan**: Path param (`:id`) tidak melewati validasi Zod seperti body/query, jadi ID yang salah format (bukan UUID valid) mengenai kolom UUID di database menghasilkan error Postgres mentah yang sebelumnya jatuh ke `500 internal_error` generik. - **Dampak**: Semua endpoint dengan path param UUID — respons untuk ID yang salah format berubah dari 500 menjadi 400. Tidak ada perubahan pada kasus ID valid (termasuk ID valid tapi tidak ditemukan, yang tetap 404 seperti sebelumnya).
- **Diuji oleh**: TC-NF-05 (`GET /warranty/not-a-valid-uuid` → `400 bad_request`).

## CR-009 — API base URL relatif + Vite dev proxy, bukan `http://localhost:3000` absolut

- **Tanggal**: 2026-08-23
- **Terkait**: [BUG-09](resolution.md#bug-09--forgot-password-gagal-total-failed-to-fetch-saat-spa-diakses-lewat-tunnelhost-lain-ngrok-lan-ip)
- **File diubah**: `frontend/src/api/client.js`, `frontend/vite.config.js`, `frontend/.env`, `frontend/.env.example`
- **Perubahan**: `API_BASE` fallback di `client.js` diubah dari `http://localhost:3000/api/v1` (absolut) menjadi `/api/v1` (relatif); `vite.config.js` menambahkan `server.proxy['/api'] → http://localhost:3000` supaya path relatif itu tetap sampai ke backend saat dev. `VITE_API_BASE_URL` di `.env`/`.env.example` disamakan ke `/api/v1`.
- **Alasan**: URL absolut ke `localhost` hanya valid bila browser berjalan di mesin yang sama dengan backend. `vite.config.js` sudah mendukung akses SPA dari luar lewat tunnel ngrok (`allowedHosts`), tapi backend tidak ikut di-tunnel -- browser yang mengakses lewat tunnel me-resolve "localhost:3000" ke dirinya sendiri dan gagal `Failed to fetch` pada setiap pemanggilan API. Path relatif + proxy membuat pemanggilan API selalu same-origin terhadap host mana pun yang menyajikan SPA, konsisten dengan topologi reverse-proxy produksi yang sudah didokumentasikan (`system.md` §14).
- **Dampak**: Semua pemanggilan API dari frontend (`apiFetch`/`apiFetchForm`/`apiFetchBlob`, termasuk link SSO) -- tidak ada perubahan pada backend maupun kontrak request/response, hanya cara frontend menentukan target URL-nya. `VITE_API_BASE_URL` absolut tetap didukung sebagai override eksplisit untuk topologi lain.
- **Diuji oleh**: Vite dev server direstart; `POST https://walleye-tidy-radically.ngrok-free.app/api/v1/auth/password/forgot` (via curl, mensimulasikan request browser lewat tunnel publik) → `202 Accepted` dengan body normal. `npm run build` frontend sukses. `grep -r "localhost:3000" frontend/src` kosong.

## CR-011 — Batasi scope cache-first service worker ke `SHELL_ASSETS` + naikkan `CACHE_NAME`

- **Tanggal**: 2026-08-23
- **Terkait**: [BUG-10](resolution.md#bug-10--reset-password-dan-halaman-lain-tetap-failed-to-fetch-setelah-fix-bug-09-karena-service-worker-menyimpan-cache-modul-js-lama)
- **File diubah**: `frontend/public/sw.js`
- **Perubahan**: `fetch` handler sekarang hanya menerapkan cache-first ke path yang persis ada di `SHELL_ASSETS` (`/`, `/manifest.webmanifest`, `/icon.svg`), bukan ke seluruh `GET` same-origin selain `/api/`. `CACHE_NAME` dinaikkan dari `custportal-shell-v1` ke `custportal-shell-v2` supaya `activate` handler yang sudah ada membuang cache lama (termasuk modul JS yang terlanjur ke-cache secara salah) pada browser yang pernah mengunjungi SPA sebelum fix ini.
- **Alasan**: Fetch handler lama menerapkan cache-first ke *setiap* request `GET` same-origin (semua modul JS/CSS yang disajikan Vite, semua navigasi rute SPA), bertentangan dengan komentarnya sendiri yang menyatakan niatnya "app shell only". Karena mode dev tidak memakai nama file ber-hash, modul seperti `src/api/client.js` yang sempat ke-cache pada versi lama (mis. saat masih membawa bug BUG-09, `API_BASE` absolut ke `localhost:3000`) tersimpan permanen di service worker browser tsb -- perbaikan apa pun di kode sumber tidak akan pernah sampai ke browser itu sampai cache dibuang. - **Dampak**: Semua request yang dilayani frontend (dev & build) -- modul JS/CSS dan navigasi SPA kini selalu network, tidak lagi bisa "macet" di versi lama pada browser yang sudah pernah mengunjungi. Hanya 3 aset shell yang tetap cache-first (perilaku offline-shell yang memang didesain, tidak berubah). Browser yang sudah pernah mengalami BUG-09/BUG-10 akan pulih otomatis pada reload berikutnya (`skipWaiting()`+`clients.claim()` sudah ada sebelumnya) -- tidak perlu clear-cache manual.
- **Diuji oleh**: Curl terhadap `POST /api/v1/auth/password/reset` lewat URL publik ngrok (sebelum & sesudah perubahan, sama-sama `401 invalid_reset_token` normal -- mengonfirmasi jalur jaringan tidak pernah rusak, murni masalah cache browser). Diverifikasi lewat `/code-review` skill (7 sudut: correctness A/B/C, reuse, simplification, efficiency, altitude) -- tidak ada temuan pada `frontend/public/sw.js`. **Belum diverifikasi** di browser nyata yang mengalami BUG-10 (tidak ada akses browser interaktif dari sesi ini).

## CR-024 — Perlakukan respons error non-JSON (bukan kontrak `{error:{code,message}}`) sebagai "server tidak terjangkau", bukan pesan status generik

- **Tanggal**: 2026-08-24
- **Terkait**: [BUG-16](resolution.md#bug-16--login-gagal-dengan-pesan-generik-request-failed-with-status-500-saat-backend-down-alih-alih-pesan-server-tidak-terjangkau-yang-sudah-dibangun-di-cr-012), menutup celah yang tertinggal di [CR-012](#cr-012--nyalakan-ulang-proses-backend--bedakan-server-tidak-terjangkau-dari-error-api-lain-di-frontend) (BUG-11)
- **File diubah**: `frontend/src/api/client.js` (operasional: proses backend Node di-restart secara manual, tidak ada file backend yang diubah)
- **Perubahan**: Tambah `isApiErrorPayload(payload)` yang memeriksa `payload.error.message` benar-benar bertipe string. `toResult()` dan `apiFetchBlob()` sekarang melempar `networkUnreachableError()` (pesan yang sama dengan CR-012 — `"Cannot reach the server..."`, `code: network_unreachable`) untuk **setiap** response `!res.ok` yang tidak lolos pemeriksaan itu, bukan hanya untuk exception `fetch()` level jaringan seperti sebelumnya.
- **Alasan**: CR-012 (fix BUG-11) menganggap "backend tidak terjangkau" selalu membuat `fetch()` melempar exception. Itu benar untuk akses langsung, tapi topologi dev sejak CR-009 punya proxy Vite di antara browser dan backend — saat proxy gagal connect ke target (`ECONNREFUSED`), **Vite sendiri** yang menjawab ke browser dengan HTTP `500` sintetis (body kosong, `Content-Type: text/plain`), bukan Vite meneruskan kegagalan koneksi sebagai reject `fetch()`. Response itu valid secara HTTP sehingga lolos ke `toResult()`, yang gagal parse JSON dari body kosong dan jatuh ke fallback generik `` `Request failed with status ${res.status}` `` — persis gejala BUG-16, tidak bisa dibedakan dari bug aplikasi asli. `errorHandler.js` dicek ulang untuk memastikan fix ini aman: **setiap** cabangnya (`ApiError`, `ZodError`, Postgres `22P02`, fallback 500 generik) selalu mengembalikan JSON `{error:{code,message}}` tanpa pengecualian, jadi memakai "bentuk payload" sebagai penanda "apakah ini benar-benar respons dari aplikasi Express" tidak punya false-positive terhadap error asli backend.
- **Dampak**: Semua pemanggilan API dari frontend (`apiFetch`/`apiFetchForm`/`apiFetchBlob`) — pesan error untuk response `!res.ok` yang bukan kontrak JSON backend (sebelumnya `"Request failed with status X"` generik) sekarang konsisten `"Cannot reach the server..."` + `code: network_unreachable`, sama seperti kegagalan `fetch()` level jaringan yang sudah ditangani CR-012. Tidak ada perubahan pada penanganan error HTTP asli dari backend (semuanya tetap JSON valid per `errorHandler.js`, sama sekali tidak terpengaruh) maupun kontrak request/response API.
- **Diuji oleh**: `curl` ke proxy Vite dengan backend sengaja dimatikan mengonfirmasi bentuk response sintetis (500, `text/plain`, body kosong). Unit test terisolasi atas logika `toResult()` (3 skenario: proxy-down, 401 asli, 500 asli) mengonfirmasi hanya kasus proxy-down yang berubah jadi `network_unreachable` — dua lainnya tidak berubah. ## CR-047 — Nonaktifkan koneksi Odoo tanpa menghapusnya: `is_enabled` sebagai kolom sendiri, terpisah dari `status`

- **Tanggal**: 2026-09-04
- **Terkait**: melanjutkan [CR-045](#cr-045--permintaan-pelanggan-sungguhan-jadi-health-check-koneksi-odoo-dan-tolak-koneksi-duplikat), dan sekaligus konsekuensi langsungnya. Berangkat dari pertanyaan user melihat dua koneksi berstatus `connected` sekaligus di `/settings/odoo-connection` ("apakah tidak sebaiknya koneksi terakhir saja yang terhubung?"). Jawabannya tidak — routing koneksi memang per-user-per-company lewat `identity_mappings`, dan dua database Odoo berbeda (`pt_dira_staging`, `pt_dira`) memang harus hidup bersamaan. Tapi pertanyaan itu mengungkap lubang yang nyata: tidak ada cara apa pun untuk menghentikan pemakaian sebuah koneksi.
- **File diubah**: `database/migrations/0015_odoo_connections_disable.sql` (baru), `src/services/odooContext.js`, `src/services/odooConnectionService.js`, `src/repositories/odooConnectionRepository.js`, `src/controllers/odooConnectionController.js`, `src/routes/odooConnections.routes.js`, `src/controllers/odooWebhookController.js`, `src/services/userService.js`, `frontend/src/api/odooConnections.js`, `frontend/src/pages/OdooConnectionSettingsPage.jsx`, `api/openapi.yaml`
- **Perubahan**:
  1. **Kolom baru `odoo_connections.is_enabled`** (migrasi `0015`, `DEFAULT true` sehingga tidak ada baris lama yang berubah perilaku), plus dua endpoint `POST /admin/odoo-connections/{id}/disable` dan `.../enable`.
  2. **Bukan `status = 'disabled'`, padahal CHECK constraint di `0001` sudah mengizinkan nilai itu sejak awal.** Sejak CR-045, `status` bukan lagi milik admin: `odooConnectionHealth` menulisnya dari setiap permintaan pelanggan sungguhan, dan `recordSuccess()` menimpa apa pun yang bukan `'connected'`. Menulis `'disabled'` ke sana berarti permintaan sukses pertama yang masih menyentuh koneksi itu **menyalakannya kembali sendiri** — tanpa error, dan karena throttle 60 detik, munculnya intermiten. Dua fakta yang ortogonal diberi dua kolom: `status` = apa kata Odoo pada kontak terakhir (ditulis mesin), `is_enabled` = apakah portal boleh memakainya (ditulis manusia).
  3. **Gerbangnya satu tempat: `resolveIdentity`** (`odooContext.js`), sebelum pemeriksaan identity mapping — alasan penempatan yang sama persis dengan gerbang `feature` milik [CR-046](#cr-046--deteksi-modul-odoo-saat-runtime-fitur-yang-tidak-didukung-odoo-tujuan-ditolak-dengan-jelas-bukan-lewat-fault-xml-rpc). Menjawab **`503 odoo_connection_disabled`**, bentuk yang sama dengan `odoo_connection_unavailable`: dari sisi pelanggan keduanya keadaan yang sama, dan membedakannya hanya membocorkan keputusan internal admin.
  4. **Aksi admin yang menarik data dari koneksi ditolak `409 connection_disabled`** (`sync-companies`, `sync-users`), dan `POST /users` yang memetakan user baru ke koneksi mati ditolak `422 connection_disabled`. **Test Connection sengaja tetap boleh** — justru itu bayaran dari memisahkan kolom: admin bisa memastikan perbaikannya berhasil (`status` hijau pada baris yang `is_enabled = false`) sebelum menyalakannya lagi.
  5. **Webhook provisioning dari koneksi mati dijawab `200 skipped_connection_disabled`**, bukan 5xx: Odoo mengulang webhook pada respons non-2xx dan mengulang tidak pernah menolong, sementara peristiwa yang terlewat bisa disusulkan sekali jalan lewat Sync Users yang memang menyapu semua kontak Portal. Dicatat di audit log, pola yang sama dengan `skipped_conflict`.
  6. **Disable TIDAK diblokir oleh `identity_mappings`**, tidak seperti `remove()`. Justru koneksi yang punya pelanggan terpetakan itulah alasan fitur ini ada; `remove()` menolaknya, jadi selama ini koneksi yang paling perlu dihentikan adalah satu-satunya yang tidak bisa dihentikan.
  7. **Enable tidak memvalidasi kredensial.** Menyalakan koneksi yang Odoo-nya sedang mati harus tetap mungkin — kalau tidak, pemulihan bergantung pada urutan yang tidak dikendalikan admin. Konsekuensinya: enable itu murah dan cepat, dan tidak memakai jatah burst limiter karena tidak menelepon Odoo sama sekali.
- **Alasan**: Sebelum CR ini satu-satunya cara mengeluarkan koneksi dari layanan adalah `DELETE`, dan `remove()` menolak selama masih ada user terpetakan. Yang tersisa untuk admin cuma dua tindakan yang sama-sama salah: membiarkan koneksi terus melayani data dari Odoo yang seharusnya tidak dipakai lagi, atau membongkar dulu pemetaan pelanggannya. ## CR-054 — Switcher hanya menawarkan company dari koneksi yang `connected`: satu status untuk dua layar

- **Tanggal**: 2026-09-06
- **Terkait**: menutup [BUG-38](resolution.md#bug-38--company-switcher-menawarkan-pt-abc-indonesia-dari-koneksi-yang-tidak-pernah-bisa-dihubungi), dan menyetel ulang keputusan penyaringan yang sudah dua kali salah kriteria: [CR-052](#cr-052--titik-pemilihan-company-ikut-membaca-is_enabled-login-dan-post-companiesswitch-berhenti-mendudukkan-pelanggan-di-koneksi-yang-dimatikan-admin) menyaring dengan `is_enabled`, [CR-053](#cr-053--is_default-menang-selalu-koreksi-atas-cr-052-yang-memindahkan-pelanggan-lintas-database-odoo) mencabut penyaringannya sama sekali. Permintaan user langsung, disertai HTML `<select>` yang sedang tampil sebagai bukti.
- **File diubah**: `src/services/companyService.js`, `src/controllers/companyController.js`, `api/openapi.yaml`
- **Perubahan**:
  1. **`GET /companies` menyaring kolom `status`** — kolom yang sama yang dilihat admin di `/settings/odoo-connection`, jadi dua layar itu menjawab dari satu sumber. Koneksi yang terbukti tidak bisa dihubungi tidak punya data untuk ditampilkan; menawarkannya hanya memindahkan kegagalan satu klik lebih ke dalam.

     Kriterianya `!== 'error'`, bukan `=== 'connected'` — **satu-satunya penyimpangan dari permintaan user, dan disengaja**. Bedanya hanya baris `pending`: koneksi yang belum pernah dihubungi sama sekali. Untuk data yang ada sekarang keduanya identik (tidak ada baris `pending`), tapi menyembunyikan company karena status koneksinya **tidak diketahui** adalah bentuk kegagalan yang persis sama dengan BUG-37 — menghilangkan company pelanggan tanpa jejak. Hanya kegagalan yang sudah terbukti yang boleh menghilangkan pilihan.
  2. **`status`, bukan `is_enabled`** — dan justru perbedaan itu inti pelajarannya. Untuk data yang sama, kedua kriteria memberi jawaban yang **berlawanan**: `is_enabled` menyembunyikan `PT DIRA` (satu-satunya company yang cocok dengan `company_id` pelapor di Odoo) sambil membiarkan `PT ABC Indonesia` yang url-nya `does-not-exist.example.invalid`. `status` membalik keduanya dengan benar.
  3. **Company yang sedang diduduki sesi selalu ikut, apa pun statusnya.** `<select>` di `CompanySwitcher` dikendalikan `current?.id`; kalau kursinya tersaring keluar, ia menunjuk `<option>` yang tidak ada dan browser menampilkan entri pertama — layar yang menyebut company yang **bukan** tempat sesi itu berada. `companyController.list` karena itu meneruskan `req.user.currentCompanyId`.
  4. **Penyaringan tidak pernah menyisakan daftar kosong.** Array kosong dirender `"No company assigned"`, yang terbaca sebagai "admin belum memberimu perusahaan" padahal yang terjadi adalah Odoo-nya sedang tidak terjangkau.
  5. **`POST /companies/switch` sengaja tidak ikut menyaring `status`.** Ia tetap hanya menolak koneksi yang **dimatikan** ([CR-047](#cr-047--nonaktifkan-koneksi-odoo-tanpa-menghapusnya-is_enabled-sebagai-kolom-sendiri-terpisah-dari-status)). Alasannya sama dengan alasan CR-047 tetap mengizinkan Test Connection pada koneksi mati: `status` adalah potret kontak terakhir yang pulih sendiri, dan menolak berdasarkan potret itu membuat pemulihan bergantung pada urutan yang tidak dikendalikan siapa pun.
- **Alasan**: Sebelum CR ini, switcher pelapor menampilkan dua company — `PT ABC Indonesia` (koneksi `Main Odoo`) dan `PT DIRA`. Yang pertama tidak pernah bisa bekerja: `Main Odoo` menunjuk `https://does-not-exist.example.invalid`, data seed dari hari pertama repo, dan `status`-nya `error`. Menawarkannya sebagai pilihan yang setara adalah portal berpura-pura punya sesuatu yang tidak dimilikinya.

  Yang membuat pasangan CR-052/053/054 pantas dibaca bersama: pertanyaannya sejak awal **bukan** "haruskah daftar ini disaring" melainkan "disaring pakai kolom yang mana". CR-052 memilih `is_enabled` dan menyembunyikan company yang benar. CR-053 menyimpulkan dari kegagalan itu bahwa penyaringan itu sendiri yang salah, lalu mencabutnya — kesimpulan yang terlalu luas dari satu contoh. Kriteria yang benar sudah ada sejak CR-045: `status`, ditulis oleh permintaan pelanggan sungguhan, pulih sendiri, dan sudah dipakai layar admin untuk pertanyaan yang persis sama.

  Dua pagar di butir 3 dan 4 bukan hiasan: keduanya menutup satu-satunya cara penyaringan apa pun bisa berbohong — menyembunyikan kursi yang sedang diduduki, dan mengubah "Odoo Anda sedang tidak terjangkau" menjadi "Anda tidak punya perusahaan".
- **Temuan `/code-review` (skill, level high)** — 4 temuan, **satu di kode CR ini dan sudah diperbaiki**; tiga sisanya di kode lama, di luar cakupan, dan dicatat di sini supaya tidak hilang:
  1. **(CR ini, diperbaiki) Penyaringan `=== 'connected'` tidak punya jalur pulih otomatis untuk semua baris.** `status` dikembalikan ke `connected` oleh `odooConnectionHealth.recordSuccess`, yang hanya berjalan untuk sesi yang memang sedang **duduk** di koneksi itu. Koneksi kedua milik seorang user yang sempat `error` karena itu tersaring → tidak pernah dipilih → tidak pernah dihubungi → tidak pernah pulih. Dua perubahan: kriterianya dilonggarkan ke `!== 'error'` (bedanya baris `pending`, yaitu koneksi yang belum pernah dihubungi — menyembunyikan sesuatu karena statusnya **tidak diketahui** adalah bentuk kegagalan yang sama dengan BUG-37), dan komentar yang mengklaim "pulih sendiri, tidak ada yang perlu ditekan admin" diganti dengan jalur pulih yang sebenarnya: Test Connection di `/settings/odoo-connection`, yang juga menulis `status` — dan itu memang halaman yang jadi sumber aturan ini.
  2. **(Kode lama, masih terbuka — berat)** `odooConnectionService.checkConnection` mengirim kredensial Odoo tersimpan yang sudah didekripsi ke `url` yang **dikirim klien**. Dengan `{connection_id, url: "http://…", username}` tanpa `credential`, kredensial baris itu diautentikasikan ke host mana pun — setiap password/API key Odoo tersimpan bisa dipulihkan dalam bentuk teks biasa oleh pemegang sesi platform-admin. Melanggar aturan #4 `CLAUDE.md`. Sudah tercatat terbuka sejak BUG-30/BUG-31.
  3. **(Kode lama, masih terbuka)** `checkConnection` juga menstempel `status` hasil pengujian ke baris tersimpan meski targetnya belum disimpan: salah ketik URL di form lalu menekan Check Connection menulis `status='error'` ke koneksi yang sebenarnya sehat — dan sejak CR ini, itu berarti company-nya ikut hilang dari switcher setiap pelanggan.
  4. **(Kode lama, masih terbuka)** `AiProviderSettingsPage`: alur "hapus API key" tidak mengirim apa pun saat kotaknya dikosongkan, sehingga kuncinya bertahan sementara toast dan pil "Tersimpan" sama-sama melaporkan sukses.
- **Dampak**: Tidak ada migrasi, endpoint, skema, maupun dependency baru. `companyService.listForUser` menerima parameter kedua opsional (`currentCompanyId`); satu-satunya pemanggilnya adalah `companyController.list`. Untuk instalasi yang tidak punya koneksi ber-`status = 'error'` — keadaan normal — tidak ada satu pun baris yang hilang dari respons. Yang berubah hanya untuk koneksi yang benar-benar gagal dihubungi: company-nya berhenti ditawarkan.

  Satu konsekuensi yang perlu diketahui operator: pulihnya **tidak selalu otomatis**. `status` kembali `connected` lewat `odooConnectionHealth.recordSuccess`, yang hanya berjalan untuk sesi yang sedang duduk di koneksi itu — jadi koneksi yang tidak sedang diduduki siapa pun tidak bisa pulih dari lalu lintas pelanggan. Yang memutus lingkaran itu adalah **Test Connection** di `/settings/odoo-connection`, yang juga menulis `status`. Ini juga berarti temuan review #3 di atas (salah ketik URL menstempel `status='error'` ke koneksi yang sehat) kini punya akibat yang lebih terlihat daripada sebelumnya, dan pantas diperbaiki lebih dulu daripada dua temuan lama lainnya.
- **Diuji oleh**: 9 assertion baru terhadap portal DB dev sungguhan (tiga user sekali-pakai, dibuat dan dihapus dalam uji yang sama, lewat `authService.login()` yang asli), semuanya lulus: switcher pelapor kini menawarkan **hanya** `PT Dira Staging / PT DIRA` dan `PT ABC Indonesia` hilang; kolom kesehatan koneksi tidak bocor; company yang sedang diduduki tetap muncul meski `status = 'error'`, **dan** terbukti memang tersaring tanpa pagar itu (jadi yang lulus adalah pagarnya, bukan kebetulan); company sehat lain tetap ditawarkan; penyaringan tidak pernah menyisakan daftar kosong. Ditambah 10 assertion regresi BUG-37 yang dijalankan ulang seluruhnya dan tetap hijau — termasuk invarian intinya, bahwa company yang **dimatikan tapi sehat** tidak lenyap dari daftar. `node scripts/check-company-selection.js` dijalankan, `node scripts/check-assistant-invariants.js` lulus, `src/app.js` dimuat utuh, `npm run build` di `frontend/` sukses, `api/openapi.yaml` 123 path. **Belum diverifikasi hidup**: satu kali muat halaman sungguhan oleh pelapor untuk melihat `<select>`-nya.

Perilaku endpoint yang sudah ada tidak berubah sampai ada admin yang benar-benar menonaktifkan sebuah koneksi; sesudahnya, endpoint pelanggan pada koneksi itu `503 odoo_connection_disabled`, sinkronisasi company/user `409`, dan webhook provisioning-nya dijawab `200 skipped_connection_disabled` tanpa membuat user. Tidak ada dependency baru. CR-048 memperbaiki tiga hal di halaman Konfigurasi Provider AI yang semuanya berakar pada satu masalah — halaman itu meminta admin mengetik yang tidak bisa dia verifikasi lalu tidak memberi tahu apa yang terjadi sesudahnya: field model jadi dropdown yang isinya ditanyakan ke provider-nya sendiri lewat endpoint baca baru (`GET /admin/assistant/provider-configs/{provider}/models`, cache 10 menit, burst limiter sendiri karena menelepon keluar), hasil simpan diberitahukan lewat toast + baris status permanen yang isinya diambil dari respons backend (bukan asumsi), dan kotak API key yang sudah terisi menampilkan pil "Tersimpan" + mask bertitik + tanggal pembaruan alih-alih kotak kosong yang terbaca sebagai "belum diisi". Tidak ada migrasi, tidak ada perubahan skema, dan tidak ada dependency baru (toast ditulis sendiri). Backend tetap tidak pernah mengembalikan kunci API dalam bentuk apa pun — mask-nya dekoratif dan panjangnya tetap. CR-049 menyusun ulang halaman yang sama di sekitar pertanyaan utamanya ("permintaan asisten berikutnya diproses siapa, dan apakah itu akan berhasil?"): kartu provider aktif di paling atas, grid kartu provider, dan dialog konfirmasi saat berpindah. Perubahan modelnya bukan kosmetik — **"Aktif" dan "Terhubung" kini dua status terpisah** yang tampil berdampingan (migrasi `0016` menambah `health_*` di `assistant_provider_configs` plus `provider_activated_at` di `assistant_settings`), karena kombinasinya yang informatif: aktif+tidak terhubung berarti asisten sedang rusak, tidak aktif+terhubung berarti provider itu siap jadi cadangan. Endpoint `POST /admin/assistant/provider-configs/{provider}/test-connection` mengujinya lewat endpoint list-model provider, bukan panggilan chat percobaan — tombol uji tidak boleh menghabiskan token, dan kegagalan panggilan chat tidak bisa membedakan "model salah ketik" dari "kunci salah". Hasilnya tiga (`connected`/`degraded`/`error`, plus `not_configured` yang membersihkan health lama), karena "kredensial benar tapi model tidak ada di daftar provider" adalah kegagalan nyata yang tanpa nama sendiri hanya bisa dilaporkan sebagai kebohongan ke salah satu arah. Panel Provider Usage, Request Detail, indikator provider di header dan di widget chat, serta parameter per-provider sengaja belum dikerjakan. CR-050 berangkat dari laporan `401` pada `GET /notifications` yang ternyata **bukan bug** — itu siklus normal access token 15 menit yang ditemukan lalu dipulihkan sendiri oleh `apiFetch` (dibuktikan dari jarak antar-rotasi refresh token pada sesi nyata: median tepat 15 menit) — tapi penelusurannya menemukan dua cacat sungguhan: rotasi refresh token yang **tidak atomik** (dua refresh bersamaan sama-sama lolos dan meninggalkan dua token aktif untuk satu sesi, sehingga sifat sekali-pakai tidak pernah ditegakkan; terbukti dari tiga sesi di DB dev yang token aktifnya lahir berselisih 5–18 ms) dan `NotificationBell` yang menelan semua kegagalan dengan `catch {}` kosong sehingga "401 lalu pulih" dan "401 lalu mati total" terlihat identik dari layar. Rotasi kini bersyarat `status='active'` dan refresh diserialkan antar-tab lewat Web Locks — keduanya wajib berpasangan, karena memperketat rotasi tanpa serialisasi justru memaksa logout pengguna multi-tab, regresi yang ditangkap `/code-review` sebelum sempat dikirim. Tidak ada migrasi, endpoint, maupun dependency baru. CR-051 menutup sisanya: laporan `401` yang sama masuk **dua kali**, dan yang kedua ternyata bug sungguhan — regresi CR-050 sendiri (BUG-34), satu karakter `()` sisa IIFE yang membuat setiap `refreshSession()` melempar `TypeError` sehingga `apiFetch` memanggil `clearSession()`: logout paksa tiap 15 menit, lolos `npm run build` maupun `/code-review` karena tidak ada satu pun pemeriksaan yang MENJALANKAN `client.js`. Perbaikannya satu karakter; yang penting adalah `scripts/check-auth-refresh.mjs` yang kini mengimpor file itu apa adanya (dengan `fetch`/`localStorage` di-stub) dan menjalankan 9 skenario sesi — dan sudah dibuktikan merah untuk regresi itu, bukan sekadar hijau. Sekalian, kedaluwarsa access token kini dihitung dari `exp` token itu sendiri dan di-refresh 60 detik sebelumnya, jadi `401` berkala hilang dari operasi normal dan turun pangkat jadi jaring pengaman untuk timer yang telat, laptop yang bangun dari tidur, dan jam yang meleset. CR-052 menutup lubang yang ditinggalkan CR-047 sendiri (BUG-36): kolom `is_enabled` yang diperkenalkan di sana hanya dibaca oleh gerbang di titik konsumsi (`resolveIdentity`), sementara ketiga titik yang MEMILIH company untuk sebuah sesi -- `issueSession` saat login, `GET /companies`, dan `POST /companies/switch` -- tidak tahu kolom itu ada, sehingga satu klik "Nonaktifkan" mendudukkan pelanggan pada koneksi mati dan seluruh portal menjawab `503` tepat sesudah login berhasil (4 dari 8 user aktif di DB dev terkunci total saat ditemukan). Login kini mendahulukan company yang koneksinya hidup meskipun bukan default-nya, daftar company menyaring yang mati, dan `switch` menolak `503` lewat guard yang sama persis dengan `resolveIdentity` -- kecuali bila SELURUH company user mati, yang sengaja tetap didudukkan supaya pesannya "hubungi administrator" alih-alih "select a company first" yang tidak mungkin ditindaklanjuti. Tidak ada migrasi, endpoint, maupun dependency baru; satu-satunya perubahan kontrak adalah respons `503` baru pada `POST /companies/switch`. Pelajaran yang dicatat sebagai kelas, bukan insiden: setiap gerbang baru di choke point berpasangan dengan satu pertanyaan -- siapa yang memilih nilai yang akan diadili gerbang itu, dan apakah dia tahu? CR-053 kemudian membatalkan sebagian CR-052 sendiri, karena jawaban CR-052 atas pertanyaan itu terlalu jauh: ia mendahulukan "koneksi yang menyala" DI ATAS `is_default`, dan `is_default` ternyata bukan preferensi tampilan melainkan jawaban Odoo atas "pelanggan ini duduk di mana" (diisi CR-040 dari `company_id` kontaknya sendiri). Karena company lain milik seorang user hampir selalu berada di KONEKSI lain -- yang berarti DATABASE Odoo lain -- "pindah satu langkah ke koneksi yang menyala" secara harfiah memindahkan pelanggan dari partner 8 di `pt_dira_staging` ke partner 125 di `prod`: bukan company cadangan, melainkan identitas pelanggan yang lain (BUG-37, dan persis kelas kesalahan yang sudah diperingatkan BUG-32). `is_default` kini menang selalu; kesehatan koneksi -- kini termasuk `status`, bukan cuma `is_enabled` -- hanya jadi tiebreak saat default itu memang tidak ada, dan `GET /companies` berhenti dipangkas karena menyembunyikan company berarti menyembunyikan identitas Odoo pelanggan. Yang paling perlu diingat dari pasangan CR ini bukan kodenya: verifikasi CR-052 DIJALANKAN dan hijau, 10 assertion, dan tidak satu pun bertanya apakah company yang terpilih milik pelanggan yang benar -- semuanya bertanya apakah ia bisa dipakai. Uji yang menguji perilaku yang salah akan hijau dengan sempurna. CR-054 kemudian menyetel ulang satu butir CR-053: mencabut penyaringan `GET /companies` sama sekali ternyata kesimpulan yang terlalu luas dari satu contoh, karena yang salah pada CR-052 bukan penyaringannya melainkan KOLOMNYA. Untuk data yang sama `is_enabled` dan `status` memberi jawaban berlawanan -- `is_enabled` menyembunyikan `PT DIRA` (satu-satunya company yang cocok dengan `company_id` pelanggan di Odoo) sambil membiarkan `PT ABC Indonesia` yang url-nya `does-not-exist.example.invalid`; `status` membalik keduanya dengan benar. Switcher kini menyaring `status = 'connected'`, status yang sama yang dilihat admin di `/settings/odoo-connection` sehingga dua layar itu menjawab dari satu sumber, dengan dua pagar yang menutup satu-satunya cara penyaringan bisa berbohong: company yang SEDANG diduduki sesi selalu ikut apa pun statusnya, dan penyaringan tidak pernah menyisakan daftar kosong. Benang merah CR-052/053/054 -- dan alasan ketiganya pantas dibaca bersama -- adalah bahwa `odoo_connections` punya dua kolom kesehatan yang mirip tapi menjawab pertanyaan berbeda (`status` = apa kata Odoo pada kontak terakhir, ditulis mesin; `is_enabled` = apakah portal boleh memakainya, ditulis manusia, sebagaimana sudah tertulis di migrasi `0015` sejak awal), dan setiap kali salah satunya dipakai untuk pertanyaan milik yang lain, hasilnya bug.
